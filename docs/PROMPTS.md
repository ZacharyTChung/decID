## Appendix: prompt 1 (full text)

````text
Act as a senior blockchain architect, full-stack Web3 engineer, and security-focused technical lead. Build a complete, developer-friendly prototype of a privacy-conscious decentralized identity system.
I want working code in this repository, a usable interface, executable tests, and clear documentation. Do not stop at an architecture proposal or disconnected boilerplate.
1. Product goal and scope
Build a digital identity MVP with three roles:

* Holder: a person who controls an Ethereum wallet and receives a credential.
* Issuer: a simulated trusted identity office that approves requests and signs credentials.
* Verifier: a service that checks a credential and confirms that the presenter controls its subject wallet.

The core demo must show a holder receiving a signed “Identity Verified” credential, keeping it off-chain, registering an issuer-authorized commitment on a local EVM chain, presenting the credential, and accessing a small contract-gated action. The issuer must be able to revoke it, after which verification and the gated action fail.
Use synthetic identity information only. This is a prototype of the technical trust and verification flow, not real government identity verification.
Implement one credential type well. Explain how a health or vaccination credential could use the same architecture later, but do not build a second product, actual healthcare integrations, or medical decision logic.
2. How to work in this repository
First inspect the repository, package manifests, existing implementation, project instructions, and relevant uncommitted changes. Reuse compatible work and preserve unrelated changes. If there is an existing handoff or architecture document, read it before changing anything.
If this is a fresh repository, scaffold the application. If existing code conflicts with this request, make the smallest coherent changes needed and document the decision.
Briefly state your plan, then implement it. Make reasonable, reversible choices without repeatedly asking me to choose libraries or approve routine steps. Ask only if missing information blocks meaningful progress or an action would be destructive.
Check current official documentation for version-sensitive APIs. Pin compatible dependencies and commit the lockfile. Do not invent library APIs or claim standards compliance based on JSON field names alone.
Work in small, runnable increments. Finish the core flow before optional polish. Do not use mock verification, hard-coded success responses, or an in-memory JavaScript object as a substitute for the actual blockchain.
Do not deploy to a public chain, spend real funds, publish externally, or require paid services. Local deployment and local test accounts are sufficient.
3. Default implementation stack
Unless the repository already has a compatible stack, use:

* Frontend: Next.js, React, TypeScript, and Tailwind CSS.
* Backend: Next.js server routes with clearly separated issuer, verifier, authentication, and credential modules.
* Blockchain: Solidity, Hardhat, and a local Hardhat network.
* EVM integration: ethers.js v6.
* Contract libraries: compatible OpenZeppelin access-control, cryptography, and EIP-712 components.
* Credential cryptography: a maintained JOSE implementation such as jose, plus suitable DID libraries.
* Local server persistence: SQLite through a lightweight maintained library.
* Testing: the contract framework’s tests, an appropriate TypeScript test runner, and a scripted end-to-end demo.
* Package management: npm, unless the existing repository uses another manager.

Use one application plus the contract workspace; avoid microservices, Kubernetes, elaborate monorepo tooling, and unnecessary dependencies. State the required Node.js version.
The MVP must run without an external RPC subscription, external identity provider, IPFS account, or paid infrastructure.
4. Identity and credential standards
Choose the W3C DID approach for this MVP. Do not also implement ERC-725 or Solana.
Prefer a DID Core-compatible did:key for the issuer’s credential signing key and did:pkh for the holder’s EVM account, provided compatible libraries support the required operations. Explain and document any justified substitution before implementing it.
Requirements:

* Show exactly how holder DIDs are derived and how the verifier maps a holder DID to an EVM account and chain.
* Validate supported DID methods and identifier syntax.
* Bind the issuer’s credential verification key, issuer DID, and authorized EVM attestation signer through an explicit trusted configuration.
* Do not accept an arbitrary self-issued DID as a trusted issuer.
* Resolve or derive issuer key material using a maintained implementation. Do not trust a public key supplied by the credential presenter.
* Separate identifier syntax, wallet-control proof, issuer trust, and real-world identity verification. They are different checks.
* Explain that choosing a DID method does not mean W3C endorses that method.

Use W3C Verifiable Credentials Data Model 2.0 and a documented JOSE securing profile. Prefer the current VC-JOSE-COSE profile supported by the chosen libraries.
Include correct context, credential type, issuer, subject, unique credential identifier, and validity fields. Define the custom credential terms and versioned validation schema; do not copy example-only contexts into a supposedly real profile.
Use the correct JOSE payload shape, protected headers, key identifiers, and media type for the selected profile. Enforce a small algorithm allowlist and reject unsigned or unsupported algorithms.
If JWT registered claims duplicate VC fields, validate that the values agree. Explain the difference between decoding a token and verifying its signature and semantics.
Do not call a custom EIP-712 message a W3C Verifiable Credential or standardized Verifiable Presentation. If holder presentation uses an application-specific protocol, label it accurately and document its format.
5. Privacy model and minimal disclosure
The issuer may inspect synthetic application data off-chain. The credential itself should contain only what the verifier needs, such as the holder DID and an issuer-asserted identityVerified claim.
Do not include the applicant’s full name, date of birth, document number, address, document images, or medical information in the minimal credential or on-chain record.
Never put raw identity inputs, complete credential tokens, private commitment salts, or private signing keys in:

* Contract storage, events, calldata, or transaction input.
* Public URLs, query parameters, analytics, or ordinary application logs.
* Browser-exposed environment variables, source maps, or client bundles.

Only public contract configuration may use frontend-exposed environment variables.
The ledger may contain a randomized credential commitment, issuer and holder addresses, a schema identifier, validity times, and revocation state. Document every public field.
Do not describe a hash as encryption or claim that hashing low-entropy data provides anonymity. A hash of a birthdate or document number is not an acceptable privacy design.
Implement a randomized commitment over the exact signed credential bytes. A suitable construction is:
commitment = keccak256(abi.encode(domainSeparator, salt, keccak256(credentialTokenBytes)))
Use a fixed, documented domain separator and a cryptographically random 32-byte salt per credential. Keep the salt and exact token bytes in the holder’s private bundle. Specify the exact byte encoding and provide a deterministic test vector.
Do not hash a parsed and re-serialized token. Do not create a circular dependency by inserting the final commitment into the credential being committed.
The on-chain authorization must bind the commitment to the holder, issuer, schema, and validity window.
Be explicit about remaining disclosure: wallet addresses, issuer relationships, schema meaning, timestamps, transactions, and repeated presentations may be linkable. This is a data-minimized, pseudonymous MVP, not an anonymous or zero-knowledge system.
If you discuss proving “over 18,” distinguish an issuer-signed age predicate from a zero-knowledge proof. ZK circuits and selective-disclosure cryptosuites belong in the roadmap unless already implemented and verified.
6. Trust boundaries and signing keys
Use separate concepts for:

1. The issuer’s off-chain credential signature.
2. The issuer’s EVM registration authorization.
3. The holder’s proof of wallet control.

If separate key types are required, keep them separate and explain their trusted binding.
Generate development signing material during setup into ignored local files or server-only environment configuration. Never embed issuer private keys in frontend code or commit generated secrets.
Use clearly labeled local development accounts. Never request a real wallet’s seed phrase or private key. Browser wallet signing should use an injected EIP-1193 provider.
Issuer approval endpoints must enforce server-side authorization. A hidden button or frontend role switch is not authorization.
Use a documented wallet-sign-in flow, such as SIWE with a maintained library, or an equally explicit signed challenge protocol. Protect privileged routes with expiring server-validated sessions.
If issuer, holder, and verifier run in one application for simplicity, keep their logic separated. Demonstrate that the verifier does not require the issuer’s private signing key.
7. Smart contracts and on-chain verification
Implement a focused CredentialRegistry contract and a small DemoGate consumer contract.
CredentialRegistry should support:

* Admin-controlled issuer authorization and removal.
* Credential registration only with a valid authorization from a currently trusted issuer.
* Holder binding: a different account cannot register or use another holder’s credential.
* Permanent uniqueness of each registered commitment, including after revocation.
* Validity windows and expiration.
* Revocation by the issuing issuer; any admin override must be explicit and tested.
* Public, minimal read functions for verification.
* Minimal events containing no private payloads.

Prefer EIP-712 registration authorizations that bind:

* Credential commitment.
* Holder address.
* Issuer address.
* Credential schema identifier.
* validFrom and expiresAt.
* Authorization submission deadline.

The EIP-712 domain must bind the chain ID and registry contract address.
Use audited signature recovery utilities. Check recovered signer authorization, all signed fields, address validity, validity-window consistency, submission deadline, and duplicate registration.
Implement replay protection explicitly. A permanent consumed commitment may be sufficient for this one-registration-per-credential design; if you use nonces, explain their scope and consumption rules. EIP-712 alone does not prevent replay.
For this MVP, holder-submitted registration with msg.sender matching the authorized holder is acceptable. Do not add a relayer unless necessary.
isCredentialValid must check that the record exists, is not revoked, has an active issuer, is within its validity window, and matches the expected holder and schema. Missing records must never be valid.
Define the policy for removed issuers and re-enabled issuers. Avoid accidentally restoring individually revoked credentials.
DemoGate must expose one real gated action. It must validate the calling wallet and required credential schema through the registry, then reject invalid, expired, revoked, wrong-holder, and wrong-schema records.
Make this boundary explicit: the EVM verifies issuer-authorized registration and registry state; it does not parse the private VC or independently establish that someone’s identity documents are authentic.
If a requirement can be satisfied more safely with a smaller contract, explain the tradeoff and implement that design. Avoid upgradeable proxies, tokens, NFTs, payments, and general-purpose identity frameworks.
8. Complete issuance and presentation flow
Implement this complete lifecycle:

1. Holder connects a wallet and proves wallet control.
2. Application derives the holder DID for the active chain.
3. Holder submits a synthetic identity verification request.
4. Authorized issuer reviews and approves or rejects it.
5. Backend creates the minimal VC and signs it with the issuer credential key.
6. Backend creates the random commitment salt and computes the commitment.
7. Issuer signs the EIP-712 registration authorization.
8. Holder receives a private bundle containing the signed credential, salt, registration authorization, and versioned metadata.
9. Holder submits the authorized registration transaction.
10. Wallet dashboard displays the credential and current registry status.
11. Verifier creates a short-lived, unpredictable challenge for a specific verification action.
12. Holder consents to sharing the minimal credential and signs a proof binding the presentation to that challenge.
13. Verifier checks the signature, trust policy, holder binding, credential semantics, commitment, registry status, and challenge.
14. Verifier returns a precise result, and the holder can exercise the on-chain gated action while the credential is valid.
15. Issuer revokes the credential.
16. Fresh verification and the gated action fail.

The presentation proof must bind the challenge nonce, expected verifier audience/domain, holder account, intended action, relevant chain/registry, credential commitment, and expiration.
If SIWE is used for presentation, bind the credential/action context using the supported fields and validate them. Do not assume login alone proves consent to an unrelated credential presentation.
Challenges must be server-generated, short-lived, single-use, and consumed atomically. Concurrent requests must not successfully reuse one challenge.
Use the authenticated holder identity when creating requests. Do not trust an arbitrary holder address submitted in a form.
At verification, recompute the commitment from the submitted exact token bytes and salt. Match the signed credential’s subject, issuer, schema, and validity to the registered record. A valid-looking registry entry must not make an invalid token acceptable.
9. Backend and storage requirements
Organize routes around wallet authentication, holder requests, issuer review and issuance, presentation challenges, and verification.
Use shared validated request/response schemas. Return stable error codes and useful messages without leaking private input or stack traces.
Validate credential size, supported schema, signature algorithm, issuer key binding, subject DID, intended chain, time fields, and required claims. Do not fetch arbitrary URLs or untrusted remote contexts supplied by a credential.
Keep issuer records, challenge/session state, and holder wallet storage logically separate. Restrict holder access to their own requests and bundles. Restrict issuer review to authorized issuer sessions.
Persist only the synthetic issuer request data necessary for the demo and describe cleanup/retention behavior. Minimize server retention of delivered credential bundles. The verifier should not persist credential tokens or salts after verification.
For holder storage, an in-memory session plus encrypted JSON export/import is acceptable for the MVP. Clearly explain reload behavior. If you persist credentials in the browser, encrypt them.
Use standard authenticated encryption and a documented password-based key derivation function for encrypted export. Do not invent cryptography, retain export passwords, or store wallet private keys.
Do not silently use plaintext localStorage for credentials, salts, or secrets.
Add the session, request-validation, origin/CSRF, and basic abuse protections appropriate to the chosen authentication design. Keep the implementation proportionate to a local prototype.
10. User experience
Build a polished, understandable demo with three clearly labeled views.
Holder:

* Connect wallet; show address, DID, and network.
* Submit a synthetic verification request.
* Show pending, rejected, issued, unregistered, valid, expired, and revoked states.
* Inspect a minimal digital credential card and technical details on demand.
* Register on-chain, export/import the private bundle, present it, and use the gated action.
* Explain what will be shared before signing or submitting a transaction.

Issuer:

* Sign in with an authorized development account.
* Review synthetic requests and approve/reject them.
* View issued credentials and initiate authorized revocation.
* Clearly label the issuer as a simulated trust authority.

Verifier:

* Start a fresh verification request.
* Show checks and precise failure reasons.
* Display the minimum disclosed claim, not the original identity application.
* Show signature validity, issuer trust, wallet control, expiration, commitment matching, and chain status separately.

Handle missing wallets, wrong networks, rejected signatures, rejected transactions, insufficient local gas, pending transactions, RPC failures, and wallet account changes. Clear or rebind authenticated state when the wallet or chain changes.
Provide sensible empty states, accessible labels, loading states, and concise privacy explanations. Do not imply success before a transaction is confirmed.
If the cloud environment lacks an injected wallet, keep the UI honest and provide the scripted demo. Do not disguise a simulated click-through as a working wallet integration.
11. Meaningful tests
Write tests that exercise the security properties and real integrations.
Contract tests must cover:

* Authorized registration and gated access.
* Unauthorized issuer and unauthorized admin actions.
* Invalid and malleable signatures through the chosen recovery library.
* Altered holder, commitment, schema, issuer, or validity fields.
* Wrong EIP-712 chain ID or registry address.
* Expired submission authorization and duplicate/replayed registration.
* A nonexistent record, wrong holder, wrong schema, and invalid validity window.
* Not-yet-valid and expired credentials, including boundary behavior.
* Authorized revocation, unauthorized revocation, and issuer removal.
* Revoked credentials remaining unusable after attempted re-registration.

Credential and API tests must cover:

* Valid signed credential and valid presentation.
* Tampered claims, malformed tokens, unsigned/unsupported algorithms, and untrusted issuers.
* Mismatched issuer DID/key, subject account, schema, or validity metadata.
* Wrong salt, altered token bytes, and deterministic commitment encoding.
* Expired, replayed, wrong-audience, and concurrently reused challenges.
* Missing authentication, privilege escalation, and accessing another holder’s request.
* Encrypted export/import, including an incorrect password or modified ciphertext.
* Separation of the verifier from issuer private keys.

Add a privacy regression check using distinctive synthetic sentinel values: inspect transaction calldata, emitted events, and public record outputs to confirm raw identity fields, credential tokens, and salts are absent. Describe the limits of this check; it is not a formal privacy proof.
Create an automated integration/demo script using funded local development accounts that executes:
request → approve → issue → register → present → verify → gated action → revoke → rejected verification and gated action.
The script must use real signatures and the deployed local contracts. It should exit nonzero if any expected condition fails. Browser wallet automation is not required for this headless flow.
12. Developer setup and deliverables
Provide:

* Complete application and contract source.
* Compatible pinned dependencies and lockfile.
* Example environment configuration with placeholder values only.
* Setup scripts for local key generation, chain startup, contract deployment, and synthetic seed data.
* A single reproducible command for the headless demo where practical.
* Commands for development, contract tests, application tests, type checking, and production build.
* Generated ABI/address configuration shared by frontend and backend; no manual copying of deployment addresses.
* A reset procedure that intentionally clears demo state and explains what becomes invalid.

Document how to run the app from a fresh clone, connect a browser wallet to the local network, obtain local test funds, change demo roles/accounts, and run the entire demo.
If public testnet deployment is described, make it optional documentation only.
13. Architecture and security documentation
Create concise repository documentation covering:

* Product purpose and the trust assumptions.
* A Mermaid architecture diagram and sequence diagram for issuance, presentation, and revocation.
* A data-placement table: each data item, where it lives, who can read it, and its retention.
* The exact credential profile, sample synthetic payload, DID choices, and issuer trust configuration.
* Commitment encoding, EIP-712 fields/domain, challenge format, and revocation rules.
* The difference between off-chain credential verification and on-chain registry verification.
* Contract and API responsibilities.
* A short threat model describing attacker capability, implemented control, and remaining limitation.
* A small roadmap for stronger disclosure privacy, unlinkability, issuer key rotation, account recovery, and real issuer onboarding.

Explain the tradeoff between public on-chain per-credential status and privacy-preserving status approaches. Do not claim that deleting a local record erases blockchain history.
Separate implemented protections from future work. Do not claim production readiness, security auditing, healthcare compliance, official identity approval, or universal wallet interoperability.
14. Completion criteria
The task is complete only when:

1. A fresh local setup can deploy the contracts and run the application.
2. The issuer produces a cryptographically valid, minimal credential.
3. The holder can store/export/import its private bundle without exposing it on-chain.
4. Registration requires a trusted issuer authorization bound to the correct holder and deployment.
5. Verification checks both the off-chain credential and live registry state.
6. The gated contract enforces holder, schema, issuer, expiry, and revocation requirements.
7. Unauthorized, tampered, expired, revoked, mismatched, and replayed inputs are rejected.
8. The scripted lifecycle demo passes against real local contracts.
9. Relevant tests, type checks, and builds pass.
10. Documentation is sufficient for another developer to reproduce the result.

Run the checks rather than merely recommending them. Fix failures caused by your changes. If an environment restriction prevents a check, identify the exact blocker and report that check as unverified.
Do not leave TODOs, pseudocode, hard-coded credentials, fake signatures, or placeholder verification in the core path.
If the session is interrupted, keep a concise HANDOFF.md with completed work, important decisions, exact commands/results, blockers, and the next concrete step. Never put secrets or credential payloads in that file.
15. Final response
Keep your final response practical:

* What was built and the main architecture decisions.
* Exact quick-start and demo commands.
* Tests/checks actually run and their outcomes.
* Important privacy/trust limitations.
* Any remaining blockers or incomplete requirements.

Write the code into the repository. Do not paste the entire project into the chat or finish with only a plan.
Primary references to consult as needed:

* W3C DID Core: https://www.w3.org/TR/did-core/
* W3C Verifiable Credentials Data Model 2.0: https://www.w3.org/TR/vc-data-model-2.0/
* W3C VC-JOSE-COSE: https://www.w3.org/TR/vc-jose-cose/
* EIP-712: https://eips.ethereum.org/EIPS/eip-712

Start by inspecting the repository, state your implementation plan briefly, and then build the MVP.
````
