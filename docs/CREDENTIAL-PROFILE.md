# Credential profile, identifiers and protocol formats

This document specifies exactly what the code produces and accepts. Where it follows a standard, the standard is named. Where it is application-specific, it says so.

## DID choices

- **Issuer: `did:key` (Ed25519, multicodec `0xed01`, multibase `z6Mk…`).** The DID is the public key, so no registry or network lookup is needed. Derivation and resolution use the maintained `@digitalbazaar/did-method-key` driver with `@digitalbazaar/ed25519-multikey`. The verification method id (`kid`) is `did:key:<mb>#<mb>`.
- **Holder: `did:pkh:eip155:<chainId>:<EIP-55 address>`** (CAIP-10 account). It is derived by string formatting from the connected wallet and the active chain (`src/lib/shared/did-pkh.ts`). The verifier maps it back by strict parsing: method `pkh`, namespace `eip155`, decimal chain id without leading zeros, 40-hex address with a valid EIP-55 checksum if mixed-case, no DID URL parts. The chain must equal the deployment chain, and the address must equal the presenter that signed the proof.
- Choosing these methods does **not** mean W3C endorses them. DID Core defines the data model, and methods are registered independently. `did:pkh` and `did:key` are community specifications.

Identifier syntax, wallet control, issuer trust and real-world identity are four separate checks (see ARCHITECTURE.md). Each verifier check is reported independently.

### Adaptation: did:key → JsonWebKey

VC-JOSE-COSE asks that verification material from controlled identifier documents be `JsonWebKey` with `publicKeyJwk`. The Digital Bazaar driver resolves did:key to a `Multikey` verification method. We convert it with the same library's `toJwk` and expose a `JsonWebKey` view. The trust policy also pins the expected JWK and kid, and resolution must reproduce them exactly. Because of this adaptation, **we do not claim full VC-JOSE-COSE conformance for key discovery.**

## Issuer trust configuration

`config/trusted-issuers.local.json` (generated by `npm run setup`; see `config/trusted-issuers.example.json`):

```json
{
  "version": 1,
  "issuers": [{
    "name": "Simulated Identity Office (local development only)",
    "did": "did:key:z6Mk…",
    "kid": "did:key:z6Mk…#z6Mk…",
    "publicKeyJwk": { "kty": "OKP", "crv": "Ed25519", "x": "…" },
    "evmAttestationSigner": "0x…",
    "credentialTypes": ["IdentityVerifiedCredential"],
    "schemaIds": ["0x85879d7d1c3284670dfb12c110f22f58f78d24870630e6747af5bccf086f84c6"]
  }]
}
```

It binds three otherwise independent things out of band:

1. the **issuer DID** that appears in credentials,
2. the **credential verification key** (kid + JWK), which must also match did:key resolution,
3. the **EVM attestation signer**, which must be the `issuer` recorded on-chain for the commitment.

A self-issued `did:key` that is not listed fails with `ISSUER_NOT_TRUSTED`. Keys in token headers (`jwk`, `jku`, `x5u`, `x5c`, …) are rejected outright. The verifier never uses a key supplied by the presenter.

## Credential: `IdentityVerifiedCredential` v1

- Data model: **W3C VC Data Model 2.0**.
- Securing: **VC-JOSE-COSE §3.1.1, JWS compact serialization**. The unsecured credential *is* the JWS payload, with no `vc` claim. Media type `application/vc+jwt`.
- Protected header: `{"alg":"Ed25519","typ":"vc+jwt","cty":"vc","kid":"<issuer DID URL>"}`.
- Algorithm allowlist: `Ed25519` only (fully-specified EdDSA, RFC 9864). `none`, HMAC, `EdDSA` and every other algorithm are rejected before and during verification.
- Validation schema: zod definition `IdentityVerifiedCredentialV1` (`src/lib/shared/credential-profile.ts`). The JSON Schema generated from it is served at `/schemas/identity-verified/v1.json`.
- Custom terms: JSON-LD context `https://did-mvp.invalid/contexts/identity-verified/v1`, bundled in code and served read-only at `/contexts/identity-verified/v1`. `.invalid` is a reserved TLD (RFC 2606), chosen so these prototype IRIs cannot be mistaken for live resources. Verifiers accept only the exact `[VC v2 context, this context]` pair and never fetch contexts. Example-only contexts (`…/credentials/examples/v2`) are rejected. A production profile would host the context and schema at a stable HTTPS origin it controls.

Sample synthetic credential (decoded payload):

```json
{
  "@context": ["https://www.w3.org/ns/credentials/v2", "https://did-mvp.invalid/contexts/identity-verified/v1"],
  "id": "urn:uuid:5aa8224a-af8d-4f4e-a316-9e57282ed108",
  "type": ["VerifiableCredential", "IdentityVerifiedCredential"],
  "issuer": "did:key:z6MkjdiFVCEuoVPCvD4d7HpsxLSAohCFRPn6AMSYooTTaPzx",
  "validFrom": "2026-10-22T03:40:58Z",
  "validUntil": "2027-10-22T03:40:58Z",
  "credentialSubject": {
    "id": "did:pkh:eip155:31337:0x3C44CdDdB6a900fa2b585dd299e03d12FA4293BC",
    "identityVerified": true
  },
  "credentialSchema": { "id": "https://did-mvp.invalid/schemas/identity-verified/v1.json", "type": "JsonSchema" },
  "credentialStatus": { "type": "EvmCredentialRegistryStatus2026", "chainId": 31337, "registry": "0x5FbDB2315678afecb367f032d93F642f64180aa3" },
  "iss": "did:key:z6MkjdiFVCEuoVPCvD4d7HpsxLSAohCFRPn6AMSYooTTaPzx",
  "sub": "did:pkh:eip155:31337:0x3C44CdDdB6a900fa2b585dd299e03d12FA4293BC",
  "jti": "urn:uuid:5aa8224a-af8d-4f4e-a316-9e57282ed108",
  "iat": 1792640458,
  "exp": 1824176458
}
```

Minimal disclosure: the subject may contain only `id` and `identityVerified: true`, and any extra subject property fails validation. No name, birth date, document number, address, image or health data is ever included. `credentialStatus` names the intended chain and registry. It does **not** contain the commitment, which would be circular because the commitment is computed over the signed token.

### Duplicated JWT claims

The spec says JWT claims should not conflict with VC properties. The issuer sets them identically, and the verifier rejects any disagreement (`JWT_CLAIM_MISMATCH`): `iss = issuer`, `sub = credentialSubject.id`, `jti = id`, `iat = validFrom`, `exp = validUntil`. `nbf` is never set (VC-JOSE-COSE: NOT RECOMMENDED).

### Decoding vs verifying

Decoding base64url segments is **not** verification: anyone can produce any JSON. The verifier decodes only the protected header before verification, for the algorithm, `typ`/`cty`, forbidden headers and `kid`. It selects the key from the trust policy, verifies the signature with `jose.compactVerify` and the allowlist, and only then parses and validates the payload. The UI's “technical details” view is labelled as decoded, not verified.

## Commitment

```
tokenBytes  = UTF-8 bytes of the exact compact JWS string received (ASCII; never re-serialized)
domain      = keccak256("did-mvp:credential-commitment:v1")
            = 0xd56ab0b39608399acbb848ac88eb83405436002381faae47f6678f9e4abf71dd
salt        = 32 bytes from a CSPRNG, new per credential, kept only in the holder bundle
commitment  = keccak256(abi.encode(bytes32 domain, bytes32 salt, bytes32 keccak256(tokenBytes)))
            = keccak256(domain ‖ salt ‖ keccak256(tokenBytes))     (96-byte concatenation)
```

`CredentialRegistry.COMMITMENT_DOMAIN` exposes the same constant, which a test asserts.

**Deterministic test vector** (`test/unit/commitment-did.test.ts`):

| | value |
| --- | --- |
| token | `eyJhbGciOiJFZDI1NTE5IiwidHlwIjoidmMrand0In0.eyJ0ZXN0IjoidmVjdG9yIn0.c2lnbmF0dXJl` |
| salt | `0x000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f` |
| keccak256(tokenBytes) | `0x1a1a8546e5bcc2c6c86cb305a8fb4fb6acbfa2f27746ce89c69d7fa61d16921e` |
| commitment | `0x4b428ae5a3b00afd1da99c45c3f6b4ee29a73d020c484c33633e849d87caf38e` |

A hash is not encryption. The commitment hides the token only because the 256-bit salt is secret and random. Hashing low-entropy data such as a birth date would not hide it, and this design never does that.

## EIP-712: registration authorization (verified on-chain)

```
domain = { name: "CredentialRegistry", version: "1", chainId, verifyingContract: <registry address> }
RegistrationAuthorization(bytes32 commitment, address holder, address issuer, bytes32 schemaId,
                          uint64 validFrom, uint64 expiresAt, uint64 issuerEpoch, uint64 deadline)
```

- `schemaId = keccak256("https://did-mvp.invalid/schemas/identity-verified/v1.json")` = `0x85879d7d…f84c6`.
- `validFrom`/`expiresAt` equal the VC's `validFrom`/`validUntil` (unix seconds), and the verifier checks this equality.
- `deadline` is the submission deadline: min(issuance + 24 h, expiresAt − 1). It is inclusive (`block.timestamp <= deadline`).
- `issuerEpoch` must equal the issuer's current epoch, so authorizations signed before an issuer removal can never be used.
- **Replay protection:** EIP-712 alone does not prevent replay. The registry permanently marks each commitment as used, including after revocation, so an authorization can succeed at most once. No nonces are needed because one authorization corresponds to exactly one commitment. Cross-chain and cross-deployment replay is prevented by the domain's `chainId` and `verifyingContract`.

## Presentation proof (application-specific, verified off-chain)

**This is not a W3C Verifiable Presentation.** It is a custom EIP-712 message proving wallet control for one verifier challenge:

```
domain = { name: "CredentialPresentation", version: "1", chainId, verifyingContract: <registry address> }
PresentationProof(string statement, string audience, string action, bytes32 challenge,
                  address holder, bytes32 commitment, uint64 expiresAt)
statement = 'I consent to share my Identity Verified credential (holder DID, issuer, validity,
             identityVerified=true) with <audience> for the action "<action>".'
```

Submission: `POST /api/verifier/presentations` with `{ challengeId, credentialJwt, salt, proof: { holder, commitment, expiresAt, signature } }`.

The verifier rebuilds the typed data from **its own stored challenge** (nonce, audience = `APP_ORIGIN`, action, chain, registry) and the recomputed statement. It recovers the signer and requires `signer == proof.holder`, with `now < expiresAt <= challenge.expiresAt`. A proof for another audience, action, nonce, chain or registry therefore recovers a different address and fails. SIWE is used only for app sessions. A login never counts as consent to a presentation.

## Challenge format and lifecycle

```json
{ "challengeId": "<uuid v4>", "nonce": "0x<32 random bytes>", "action": "access-verified-member-area",
  "audience": "http://localhost:3000", "chainId": 31337, "registry": "0x…", "expiresAt": <unix s>,
  "statement": "<exact consent text>" }
```

The challenge is server-generated, lives 120 s, and is single-use. It is consumed **before** any other check by a conditional `UPDATE … WHERE consumed_at IS NULL AND expires_at > now RETURNING`, so exactly one concurrent submission can consume it. Failure codes are `CHALLENGE_UNKNOWN`, `CHALLENGE_EXPIRED` and `CHALLENGE_REUSED`. Only the challenge row and an outcome code are stored. Tokens and salts are not.

## Verification order and failure codes

1. `challenge` → 2. `walletControl` (`PROOF_*`) → 3. `tokenFormat` (`MALFORMED_TOKEN`, `UNSIGNED_TOKEN`, `ALG_NOT_ALLOWED`, `BAD_TYP`, `BAD_CTY`, `FORBIDDEN_HEADER`, `MISSING_KID`) → 4. `issuerTrust` (`ISSUER_NOT_TRUSTED`, `KID_MISMATCH`, `KEY_MISMATCH`, `KEY_RESOLUTION_FAILED`, `TYPE_NOT_AUTHORIZED`) → 5. `tokenSignature` (`BAD_SIGNATURE`) → 6. `credentialSemantics` (`SCHEMA_INVALID`, `ISSUER_KID_MISMATCH`, `JWT_CLAIM_MISMATCH`) → 7. `validityWindow` (`NOT_YET_VALID`, `EXPIRED`) → 8. `deploymentBinding` (`WRONG_DEPLOYMENT`, `BAD_SUBJECT_DID`, `SUBJECT_WRONG_CHAIN`) → 9. `holderBinding` (`SUBJECT_NOT_PRESENTER`) → 10. `commitment` (`COMMITMENT_MISMATCH`) → 11. `registry` (`NOT_REGISTERED`, `REVOKED`, `REGISTRY_EXPIRED`, `REGISTRY_ISSUERINACTIVE`, `REGISTRY_NOTYETVALID`, `REGISTRY_MISMATCH`, `RPC_UNAVAILABLE`).

Checks after the first failure are reported as `skipped` (“not reached”).

## Revocation rules

- Only the issuer address recorded for a commitment can `revoke` it, even after that issuer is removed. Revocation is permanent.
- The admin can `adminRevoke` any record, and the event records `adminOverride = true`.
- A revoked commitment can never be registered again.
- Removing an issuer immediately makes all its records `IssuerInactive`. Re-adding it starts a new epoch, so old records stay invalid and old authorizations are rejected (`StaleIssuerEpoch`).
- Expiry is `block.timestamp >= expiresAt` on-chain and `now >= validUntil` off-chain. Validity starts at `validFrom` inclusive.
- Credentials that are issued but never registered cannot pass verification, because the registry check fails, and they cannot be revoked on-chain. They simply expire.
